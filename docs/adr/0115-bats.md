# 0115. Bats' test files, and each Bats test

- **Status:** accepted
- **Date:** 2026-11-24
- **Rules:** C-86, C-87, C-88, C-89; relies on C-22, C-30, C-31, C-32, C-33, C-34, C-38, C-39,
  C-40, ADR 0068, 0069, 0080, 0081

## Context

Shell projects test with Bats (bats-core): a `.bats` file of `@test` blocks, each run in a bash
process of its own, which `load`s helpers, `source`s the libraries under test and runs the
project's scripts. Nothing reached hushrun from a Bats run: COMMAND `bats test` got the pytest
adapter, which never started, so every test ran every time. Shell has no compile step, so this
decision is test reuse alone; no build block applies (B-190 to B-199 stay unused).

What a Bats test read is what its bash processes ran: the test file, the helpers it loaded, the
libraries it sourced and the scripts it ran, and what those sourced. Bats takes nothing from the
environment that would let hushrun inside, and it's often started by a path (a `test/bats`
submodule, `node_modules/.bin/bats`), which a program on `PATH` (ADR 0080) can't reach. Bash
itself can: a non-interactive bash reads the file `BASH_ENV` names before its first command, in
every bash process, bats' own and the scripts its tests start, as long as the environment reaches
it. A spike on bats-core 1.10.0 (Ubuntu 24.04's) and 1.13.0, with bash 5.2, proved the rest.

## Decision

1. **A unit is a `.bats` file, a test is a `@test`** (C-30, C-39, C-87). Its id is its
   description, verbatim, as bats prints it; bats refuses two tests of one file with one function
   name, but a description two tests share (one `bats_test_function` gives) is never left out
   (C-39's `neverLeftOut`).
2. **Loading through `BASH_ENV`** (C-86). hushrun writes its hook to its cache and sets
   `BASH_ENV` to it, keeping the one COMMAND's environment had (`HUSHRUN_BATS_ENV_WAS`), which the
   hook reads after itself. In a process that isn't one of this run's bats the hook only notes; in
   one that is, it also says what its test file or test came to. The hook changes nothing a
   process does: what bats prints, its exit code and every test's own environment are as without
   it (ran: the same bytes, both versions, with failures, skips, retries and a failing
   `setup_file`).
3. **What a test read: the files its commands ran from** (C-87). A DEBUG trap, with `set -T` so
   that functions, subshells and command substitutions have it too, notes the file of each command
   as it is about to run (`BASH_SOURCE`): the scripts bash ran, the files `source`, `.`, `load` and
   `bats_load_library` read, and whatever those loaded, in the test's bash process and in every
   bash process it started. A file that only defines functions none of which runs is noted when
   the word `source` or `.` names expands with no side effect; a script that can't parse is noted
   by its name (`$0`) before its first line. `"$_"` keeps `$_` as it was. bats replaces a DEBUG
   trap with its own in its processes: there the hook gives bats' `bats_debug_trap` a first line
   that calls hushrun's, as bats sets it, so bats' stack traces are untouched. A test read what
   its own processes noted (`ran`); its test file's loading, `setup_file`, `teardown_file`, and the
   suite's `setup_suite` are read by each test of the file (`loaded`), so `reads: test` works
   (C-40).
4. **Sources are the files bash runs** (C-87): a `.bash` or `.sh` file whose `#!` line names
   bash (`/bin/bash`, `/usr/bin/env bash`, `env -S bash`), or that has none and isn't executable
   (a library only `source` reads), and a file with no `.` in its name whose `#!` line names bash
   (`bin/tool`). Every other file is rest: a `#!/bin/sh` script, which dash or `sh`'s POSIX mode
   runs without `BASH_ENV`; an executable `.sh` with no `#!` line, which bash runs in a subshell
   that never reads the hook; Python, compiled programs, fixtures. A change to one runs
   everything.
5. **How a test, a file and the suite ended, from bats' own exit traps** (C-88). The hook inserts
   one call before the `exit` of `bats_exit_trap` (a test's `state`, `passed` or `failed`, unset
   for a try bats runs again; `BATS_TEST_SKIPPED` for a skip), of `bats_file_exit_trap` (its
   `failure_reason`, `setup_file` or `teardown_file`) and of `bats_suite_exit_trap`; and before
   the first line of the main process's `bats_exit_trap`, which starts hushrun again
   (`__hushrun-bats facts`) to turn the notes into one facts file for the start. A function is
   changed only when its text is the one these versions have; otherwise nothing is said of that
   kind, and a test whose end isn't said didn't finish. Nothing reads as a pass from absence:
   a test with no end didn't finish; a test listed for its file that never started makes its file
   not run whole; a `.started` file says the start didn't say what it saw until the facts are
   written. A pass after a failure (`BATS_TEST_RETRIES`) isn't followed. A failure no test owns
   (`setup_suite`, `teardown_suite`) keeps no pass of the run.
6. **Selection by bats' own skip** (C-88). A test `reuseTests` lists gets, just before bats calls
   its `setup`, a `setup` that skips with the reason `reused by hushrun` and a `teardown` that does
   nothing; so it reads `ok 3 adds # skip reused by hushrun`, bats' count stays whole, and its exit
   code is what the other tests make it. A file `reuse` lists whole has each of its tests skip so,
   and its `setup_file` and `teardown_file` do nothing. bats' own way to skip a whole file isn't
   used: in 1.10 it runs the tests' bodies, and in 1.13 it skips nothing. A test that ran in a file
   listed whole is read as run, and so is its file. The lists reach bash as functions of quoted
   `case` words (`__hushrun-bats plan`), so any description matches exactly, in bash 3.2 too.
7. **Which COMMANDs** (C-86). `bats …` by its name or a path, through `env NAME=value`, and
   through `npx`, `bunx`, `pnpx`, `pnpm [exec]`, `yarn [exec]`, `bun x` and `npm exec [--]`. A
   wrapper (a shell line, a script, a Makefile) stays pytest's, as before. bats older than 1.10
   writes facts with an error, so nothing is observed. Windows isn't offered.
8. **What isn't seen** (C-89): a file read as data (`cat`, `grep`, `diff`, `shellcheck`) or by a
   program other than bash; a process whose environment lost `BASH_ENV` (`env -i`, `sudo`), or a
   bash in POSIX mode (`sh`, `bash --posix`); a DEBUG trap the user's code sets in place of
   hushrun's; a source that `source` reaches through `PATH`. A test that depends on them runs
   always when its file is in `tests.always`.

## Consequences

- Shell repositories reuse Bats test files and tests one by one, on the same rules as pytest's.
- A change to a `#!/bin/sh` script, or any file that isn't bash's, runs every test: honest, and
  coarse for POSIX-shell projects.
- Every bash process COMMAND starts reads the hook, outside bats too: a DEBUG trap per command
  costs a function call (a few microseconds), and `set -T` changes how a RETURN trap a user sets
  in a function reaches the functions it calls.
- The hook relies on four functions of bats' own, by name and text; a bats that renames them is
  observed less (its tests don't end), never wrongly.

## Alternatives considered

- **A `bats` on `PATH`** (ADR 0080): it misses bats started by a path, the common submodule
  setup, and still needs a way into each test's processes.
- **bats' report formatter or the TAP stream for outcomes:** a COMMAND may have its own report
  formatter, there is one slot, and TAP numbers tests across files; bats' exit traps say each
  test's end in its own process.
- **Wrapping `trap` to keep hushrun's DEBUG trap first:** bats' DEBUG trap fires inside the
  wrapper, so its failure stack traces named the hook, and bash 5.2 reported `pop_var_context`
  errors when bats called `trap` from its ERR trap, losing a failure.
- **`--filter` and `--negative-filter`:** names aren't unique across files, the filter is one
  regular expression for the run, and `--negative-filter` is 1.11's.
- **ShellSpec:** it runs specs in shells it chooses (`sh`, dash, zsh, ksh) and in one process per
  spec file, so a spec's reads can't be told apart through bash alone. Not built.
