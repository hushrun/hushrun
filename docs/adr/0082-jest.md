# 0082. Jest

- **Status:** accepted
- **Date:** 2026-11-12
- **Rules:** C-15, C-30, C-32, C-39, C-44; relies on C-31, C-34, C-35, ADR 0068, 0069, 0071, 0077,
  RFC 0004

## Context

RFC 0004 §4.3 adds Jest as the third observed runner, beside pytest and Vitest, with both units:
the test file, and the test (ADR 0077). Jest takes no plugin from the environment and keeps its
module registry to itself, which is why ADR 0071 chose Vitest first. A spike on Jest 29.7 and 30.5
found a way in that needs no file of the repository changed, and a prototype of the whole adapter.
This decision is the adapter, built from that prototype on Jest 29.7.0 and 30.5.2, Node 20.

## Decision

1. **Loading through `NODE_OPTIONS`.** hushrun writes its file and a reporter to
   `<cache dir>/adapters/jest-<hash>/` and adds ` --require <file>` to what `NODE_OPTIONS` had, so
   every Node process of COMMAND loads it: Jest's own, its workers (processes and threads), and
   any other, where it does nothing until a Jest module loads, and writes nothing. It wraps Node's
   `fs`, `child_process`, `worker_threads` and `process.dlopen` at once (graceful-fs copies `fs`'s
   functions when Jest loads it), and looks at what each CommonJS load returns, by shape, never by
   path or version: jest-config's `readConfigs`, @jest/core's `SearchSource`, a test sequencer,
   jest-runtime's `Runtime`, a test environment, ts-jest's compiler.
2. **A script that replaces `NODE_OPTIONS`** (`NODE_OPTIONS=--experimental-vm-modules jest`, the
   usual way to Jest's ES module mode) drops it, and nothing can see that from inside. Jest then
   writes nothing, and the run says so once with both fixes: keep what it had, or one line first
   in Jest's config that loads the same file from `HUSHRUN_JEST`, which hushrun sets:
   `process.env.HUSHRUN_JEST && require(process.env.HUSHRUN_JEST);`, or for an ES module config
   `import { createRequire } from 'node:module'; if (process.env.HUSHRUN_JEST) createRequire(import.meta.url)(process.env.HUSHRUN_JEST);`
   (an `await import()` fails on Jest 29, whose config loader tries `require()` first). Loaded
   late, inside `readConfigs`, the file catches Jest's configurations as Jest freezes them and adds
   itself to `NODE_OPTIONS` for the workers Jest starts after. `hushrun init` proposes the line
   where a `package.json` script that runs Jest replaces `NODE_OPTIONS`, and never writes it.
3. **Which COMMANDs**: one run of Jest, as `jest`, a path to it, `npx`, `pnpm [exec]`,
   `yarn [exec]`, `bunx`, `bun x`, `npm exec [--]`, or `node [options] …/jest/bin/jest.js`. Not
   offered, said once: watching (`--watch`, `--watchAll`), choosing files from an earlier run or
   from git (`--onlyFailures`, `--onlyChanged`, `--changedSince`, `--lastCommit`), what runs no
   test file (`--listTests`, `--showConfig`, `--clearCache`, `--init`, `--version`, `--help`), a
   `--testRunner` other than jest-circus, Bun's own runtime, and an installed Jest whose major isn't
   29 or 30. `npm test` hides which program runs, as for Vitest.
4. **The main process.** The first Jest whose `readConfigs` returns claims the run's directory;
   it gives Jest a configuration with hushrun's reporter added and a `passWithNoTests` that is
   true only when the user set it or hushrun left out every test file Jest chose. It lists every
   project's test files with `SearchSource#isTestFilePath` (the contexts come from
   `getTestPaths`, so a shard sees them all), and in the sequencer's `sort`, after Jest's filters
   and `--shard`, before any worker starts, removes the files `reuse` lists, only when that list
   equals `testFiles` and coverage is off. It tells its workers, through the environment they start
   with, whether they may leave tests out and watch; a Jest a test starts writes nothing. Each start
   reads only the `HUSHRUN_UNITS` it starts with, so an audit's second run, COMMAND again with a
   directory of its own, decides afresh.
5. **Each test file, in its worker.** A session from the runtime's first require to its teardown
   records every module Jest compiled (Node's `vm`: `Script`, `compileFunction`,
   `SourceTextModule`, `SyntheticModule`), every file opened, read or looked at through `fs`,
   every directory listed, and the direct imports the runtime resolves (Jest 30.5's
   `_resolution.resolveCjs`, Jest 29's `_resolveCjsModule`, the ES module linker, manual mocks).
   What the process read since the last test file ended is the next one's (Jest reading it and
   setting up its environment). Every repository file Node itself compiled in the process (an
   environment, a resolver, a transformer, Babel's config) is read by every test file of it.
6. **Tests.** At jest-circus's `run_start`, in collection order and before `--randomize`, each
   test gets its id: its suites' names and its own joined with ` > `, ` [k]` for the k-th of a
   file with an id another had; the same rule as Vitest's (RFC 0004 §4.2). The tests `reuseTests`
   lists get `mode = 'skip'`, so jest-circus runs none of their hooks, and a describe block whose
   every test is left out runs no `beforeAll`. A test whose id still collides, or whose names
   join to another nesting's id, is never left out. Outcomes come from the events: a test that
   ended; one skipped by its own code (`test.skip`, `describe.skip`, `test.todo`), which passed;
   one a focus or `--testNamePattern` skipped, which didn't finish; retries counted.
7. **Watching a test** (`reads: test`), Jest 29 and from 30.5 (whose runtimes say which file a
   name resolves to; 30.0 to 30.4 weren't tried, and run with `reads: file`, said once): V8's
   precise coverage through `node:inspector`, taken at jest-circus's boundaries, gives the files a
   function of which ran; a module's top level running because it was required isn't a call. What
   ran between `test_start` and the test's end is its own, `beforeEach` and `afterEach` included;
   what a `beforeAll` or `afterAll` ran is `shared` with the tests under its block; what
   collecting the file called, its setup files and its process's own code are `loaded`. A read
   inside a require is held until the require ends, and a module Jest read to compile it isn't
   one the test opened. A concurrent test, a process where ts-jest checked types, Jest's own V8
   coverage (same counters) and a runtime that can't resolve: no test's lists, so each test gets
   its file's.
8. **What makes a list unsound, decided for a run**:
   - **ts-jest checking types** reads every TypeScript file once per process, and an import only
     of types leaves no trace. Where its compiler made a language service (or ts-jest loaded and
     its compiler wasn't found), every file of a code kind is read by every test file of that
     process, and no test's lists are sent. With `isolatedModules`, each file compiles alone.
   - **Configuration**: Jest's config and what the main process compiled for it, and every
     `jest.config.*`, `babel.config.*`, `.babelrc.*`, `jest-preset.*` of a code kind, are read
     by every test file; `tsconfig*.json`, `.swcrc` and `package.json` are rest already.
   - **A new `__mocks__` file** changes what loads with no read before it: it is a new source,
     which runs everything (C-31's `shape`).
   - **A repository `testEnvironment`, resolver or transformer**: its files, and what Node compiled
     for them, are read by every test file. A cache of their own across test files isn't followed.
     An environment Node loads as an ES module is never wrapped: no event, `not observed`.
   - **globalSetup** runs in the main process, between `sort` and the run's start: what it
     compiled and opened is read by every test file, and a process or worker it starts makes every
     test file `not observed`.
   - **`projects`**: a test file in two projects is one unit, by its path: it passed when it passed
     in every project that ran it, and read what each read; leaving it out leaves it out of all.
   - **Snapshots**: a `.snap` is read by its test file alone, through `fs`, so it is a source, and
     a change to one runs its test file only. Obsolete snapshots fail a run that isn't updating
     them, so the test file that has them fails.
   - **Worker threads, child processes, native addons** of the repository's code are `not
     observed`, in the test whose window started them.
   - **A runner other than jest-circus** sends no event: every test file is `not observed`.
9. **Coverage on** observes and leaves nothing out (C-26's spirit); with the V8 provider, no test
   is watched.

## Costs

Measured on the spike's sample (30 test files, 10 trivial tests each, each file requiring 2 of 10
modules), Node 20.20.2, macOS arm64, warm transform cache, `--silent --ci`, the three settings
interleaved over 7 rounds after a warm-up, medians; CPU is user and system time of Jest and its
workers. The machine was loaded by other work (load average 30 to 50), so CPU time is the number
to read.

| Jest | Workers | No adapter (wall / CPU) | File level | Each test watched |
|---|---|---|---|---|
| 29.7.0 | 4 | 1.40 s / 2.19 s | 1.52 s / 2.67 s (CPU ×1.22) | 1.92 s / 3.41 s (CPU ×1.56) |
| 29.7.0 | in band | 1.96 s / 1.10 s | 4.18 s / 1.26 s (×1.14) | 8.16 s / 2.36 s (×2.13) |
| 30.5.2 | 4 | 1.35 s / 1.83 s | 1.61 s / 2.15 s (×1.17) | 2.06 s / 2.63 s (×1.44) |
| 30.5.2 | in band | 2.77 s / 1.43 s | 2.39 s / 1.49 s (×1.04) | 6.83 s / 3.14 s (×2.20) |

In CPU time, file level costs 0.2 to 1.6 ms a test (2 to 16 ms a test file), more on Jest 29,
whose workers resolve modules through `fs`; watching each test costs 2.7 to 5.7 ms a test, almost
all of it in V8's coverage takes. In-band wall times moved with the machine's load more than with
the adapter.

File level costs little: the wrappers record only while a test file runs, or between test files.
Watching each test takes V8's counters at each boundary, which carries every function that ran
since the last take; it is off unless a check asks for `reads: test` (RFC 0004 §5).

## Consequences

- A Jest repository is observed with no file changed, wherever COMMAND starts Jest itself.
- Jest's internals are wrapped from outside. A release that moves what the adapter holds on to
  observes nothing, and says so; each part is found by shape, and a missing one is `not observed`
  or `reads: file`, never a guess.
- ts-jest with type checking reuses only when no file of code changed; `isolatedModules` gives
  each test file its own list back.
- A script that replaces `NODE_OPTIONS` needs one of two edits a person makes.

## Alternatives considered

- **The config line first:** it is a hack around `Object.freeze`, can't live in a `package.json`
  config, and misses `--workerThreads`; `NODE_OPTIONS` reaches everything without an edit.
- **A test environment or setup file of hushrun's:** both reach only the worker; leaving out files,
  the empty-run rule and the main process's word need the main process.
- **Jest's own V8 coverage per test:** it is collected per file, not per test.
- **Every repository file as not observed under ts-jest's type check:** no reuse at all; every
  file of code read is the same truth with reuse when only data changes.
- **Leaving a file whose every test is listed out whole:** the main process doesn't know a file's
  tests before collection; jest-circus skips them all, and the file only loads.
